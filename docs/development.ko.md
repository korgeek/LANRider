## 3일 만에 만든 MVP

시작은 작은 바람이었습니다. 외부와 분리된 회사 LAN에서 동료들과 쉬는 시간에 짧게 경주하고 싶었습니다. 예전에 즐기던 레이싱 게임을 떠올리며 GPT와 이야기를 시작했고, 3일 만에 브라우저에서 플레이할 수 있는 경주 MVP를 만들었습니다.

3일은 처음 플레이할 수 있는 MVP를 만드는 데 걸린 기간입니다. 현재의 모든 기능을 그 안에 완성했거나 상용 서비스 수준으로 준비했다는 뜻은 아닙니다. 이후 멀티플레이 복구, 차량 선택, 사운드, 그래픽 설정, 연속 경기 흐름을 보강했습니다.

Three.js, Node.js, WebSocket으로 만든 데스크톱 키보드 게임입니다. 로컬 서버 하나가 게임, 모델, 텍스처, JavaScript 의존성을 제공합니다. 로그인과 데이터베이스는 없으며, 방은 서버 프로세스의 메모리에만 존재합니다. 서버를 재시작하면 방도 종료됩니다.

## 주행 물리와 판정

차량 선택 바로 아래에 일반 최고속도와 공유 물리 코드로 측정한 0–100km/h 가속 시간을 표시합니다. 일반 최고속도를 일괄 5% 낮춰 차종별 175.75~218.5km/h, 평균 190km/h로 설정했으며 부스터 상한은 280km/h입니다. 최고속도가 낮은 차량은 각자의 최고속도에 더 빨리 도달하도록 하되, 출발 가속·코너링·충돌 회복·충전·부스터의 차종별 특성을 유지합니다. 자동 주행 비교는 밸런스 점검 지표이며 실제 플레이에서 동등한 경쟁력을 보장하지는 않습니다.

일반 코너링에서는 진행 중인 속도 벡터의 관성을 유지합니다. 타이어는 가속·제동·코너링이 공유하는 힘의 한도 안에서 옆 미끄러짐을 줄이며 에너지를 잃으므로, 고속에서 크게 꺾으면 완만하게 감속하고 선회 반경이 넓어집니다. 작은 조향의 손실은 미미합니다. 구동력은 최고속도에 가까워지면 점진적으로 줄어들며, 부스터 종료 후의 초과 속도도 저항으로 감소합니다. 차축 하중 이동과 회전 관성을 생략한 질점 근사 모델이며, 접지력 수치는 실차 측정값 대신 게임의 속도·도로 크기에 맞췄습니다. `node tools/qa/cornering-balance.mjs current`로 차종별 조향 측정과 세 코스 비교를 실행하면 `.cache/`에 결과가 저장됩니다.

완주 기록은 결승선에서 확정하지만 차량은 액셀을 놓은 것처럼 관성으로 전진하며 감속합니다. 완주 차량은 아직 경주 중인 차량의 충돌을 방해하지 않으며, 결과 화면에서도 기록과 다음 출발 위치를 바꾸지 않고 감속을 이어갑니다.

역주행이 지속되면 화면 가장자리에 붉은 경고를 표시합니다. 차량 충돌은 차종별 차체 너비·길이의 90% 크기로 회전하는 직사각형 박스를 사용하고, 충돌 박스의 높이는 드라이버 전체를 포함합니다. 서버와 로컬 예측이 같은 판정을 사용하며 겉모양이 가볍게 스치는 정도는 허용합니다.

## 어떻게 만들었나

아래는 개발 과정의 요구와 결정을 돌아보며 정리한 요약입니다. 실제 대화를 그대로 인용한 내용은 아니며, 비공개 대화 전문이나 참고 이미지도 포함하지 않았습니다.

### 1. 경기 판정은 서버에서

```text
요구: 충돌, 랩 진행, 경기 결과를 모든 참가자가 같게 보아야 한다.
결정: 시뮬레이션과 경기 상태는 권한 있는 서버 하나가 관리한다.
구현: 물리는 60 Hz로 계산하고 상태 스냅샷은 20 Hz로 전송한다.
```

서버는 입력 명령을 검증하고 위치, 충돌, 체크포인트, 완주를 확정합니다. 클라이언트 예측은 조작 반응을 빠르게 만들지만 완주를 확정하지는 않습니다. 서버와 로컬 예측이 같은 물리 코드를 사용해 계산 차이를 줄입니다.

서버 프로세스 하나로 LAN MVP의 구성을 작고 이해하기 쉽게 유지했습니다. 대신 방은 일시적이며 프로세스 간 방 조정 기능이 없고, 재시작하면 연결된 경기도 끝납니다.

### 2. P2P 대신 WebSocket

```text
요구: LAN의 여러 브라우저가 같은 짧은 경주에 참가해야 한다.
결정: 모든 브라우저를 WebSocket으로 같은 서버에 연결한다.
절충: 접속·판정 구조를 단순하게 두고 참가자별 서버 통신량을 감수한다.
```

HTTP 서버 하나가 브라우저 앱을 제공하고 WebSocket 연결도 받습니다. 별도의 피어 탐색, 시그널링, 피어 간 판정 권한 흐름을 만들지 않아도 됩니다. 작은 서버 기반 게임에 맞춘 선택이며, 모든 P2P 설계보다 성능이 좋다는 주장은 아닙니다.

### 3. 먼저 반응하고 서버와 맞추기

```text
요구: 서버 왕복 응답을 기다리지 않고 조향에 반응해야 한다.
결정: 내 차량을 먼저 예측하고 입력 명령마다 번호를 붙인다.
구현: 서버 상태를 적용한 뒤 ACK된 입력을 지우고,
      아직 확인되지 않은 입력만 그 상태에서 다시 실행한다.
```

내 차량은 고정 60 Hz로 예측합니다. 서버 ACK로 이미 처리한 입력을 구분하고, 보정할 때는 미확인 명령만 재실행합니다. 경기 식별자와 스냅샷 순서 검사로 이전 경기의 상태가 새 경기에 섞이지 않게 합니다.

### 4. 보간과 화면 보정

```text
요구: 상태 전송 사이에도 상대 차량과 카메라가 부드럽게 움직여야 한다.
결정: 상대 스냅샷을 100 ms 버퍼에 두고 물리와 화면 그리기를 분리한다.
구현: 상대 차량을 보간하고 내 차량의 표시 보정량을 부드럽게 줄인다.
```

상대 차량 보간은 작은 표시 지연을 받아들이는 대신 움직임을 안정시킵니다. 주행 중 8m 이내의 상대 차량은 내 차량과 같은 충돌 예측 시점과 화면 보정을 사용하며, 8~16m 구간에서 기존 보간으로 부드럽게 전환합니다. 관전 중에는 기존 보간을 유지합니다. 내 차량도 고정 물리 스텝의 누적 시간을 사용해 스텝 사이를 보간합니다. 화면 오프셋으로 보정이 눈에 띄는 정도를 줄이되 서버 물리 상태를 바꾸지는 않습니다. 카메라는 렌더 경과 시간을 사용하며 F3에서 시간·보정 통계를 확인할 수 있습니다.

### 5. 차량 상태를 따라가는 엔진음

```text
요구: 큰 오디오 시스템 없이도 차량이 살아 움직이는 느낌을 준다.
결정: 짧은 엔진 루프 두 계열을 차량별로 고정해 재사용한다.
구현: 속도로 음높이를, 액셀·부하로 필터와 음량을 조절한다.
```

PULSE, APEX, BOLT, COMET, SLIDE, IGNIS는 sport 루프, BULWARK와 RALLY는 rough 루프를 사용합니다. Web Audio 재생 노드를 계속 유지해 업데이트마다 엔진음을 다시 시작하지 않습니다. 음향 매개변수를 부드럽게 바꾸며 주변 차량 소리는 내 차량보다 작게 들리도록 조절합니다.

충돌 효과음에는 반복 제한을 둡니다. 드리프트 소리는 드리프트 중에만 이어지고 해제하면 멈춥니다. 카운트다운과 완주 소리는 경기 이벤트에 맞춥니다. 클릭·키 입력으로 브라우저 오디오 제한을 해제하며, 페이지가 숨겨지면 엔진을 음소거하고 주행 효과음을 정지합니다. 음량·음소거 선택도 저장합니다.

**musicbysantai** 명의로 Suno에서 만든 음악 3곡과 DRAGON-STUDIO의 파도 앰비언트를 포함합니다. 음악에는 소프트웨어 MIT 라이선스와 별도 조건이 적용되며, 음악 사용과 GitHub 포크에는 Suno의 이용 조건도 적용됩니다. 이용자는 GitHub 포크 외에 음악을 별도로 또는 다른 제품에 포함해 재판매·재배포할 수는 없습니다. 원본 MP3 바이트·태그·내장 표지를 그대로 보존하며, [음악·파도 고지](../public/assets/notices/music-Suno.md)에 출처와 범위를 기록합니다. 출처가 기록된 CC0 엔진·효과음과 직접 합성한 카운트다운은 유지합니다.

방 만들기 화면에서는 음악이 기본적으로 랜덤으로 설정되며, 좌우 버튼으로 곡을 고르면 즉시 미리 들을 수 있습니다. 방은 시작 곡과 재생 방식을 공유합니다. 선택한 곡은 끝나면 다시 재생하고, 랜덤은 곡이 끝날 때 다른 곡으로 바뀔 수 있습니다. 전환할 때 짧게 페이드하며 끊김 없는 루프는 아닙니다. 대기실에 들어가면 음악이 페이드아웃하고 출발 신호가 끝난 뒤 레이스 음악이 시작됩니다. 운전 입력은 음악 재생을 재시작하지 않습니다. 상단 음소거는 채널별 저장 음량을 유지하면서 전체 소리를 끕니다. 기본 음량은 배경음 30%, 음악 50%, 효과음 20%이며 기존 저장 설정을 우선합니다.

BGM은 HTML 오디오 요소 하나로 스트리밍하며 전체 플레이리스트를 PCM으로 디코딩하지 않습니다. 실제로 선택해 재생한 곡만 압축 파일로 캐시하고, 다운로드에 실패하면 선택한 곡의 캐시를 확인하며, 랜덤 모드에서는 다른 캐시된 곡도 확인합니다. 가능한 환경에서는 CacheStorage를 쓰고, 일반 HTTP LAN에서는 페이지가 열린 동안의 메모리 캐시와 브라우저 HTTP 캐시를 활용합니다. 음악·파도·효과음·엔진음은 공통 출력의 헤드룸·컴프레서·피크 가드를 거치며, 저장되는 각 채널 음량은 독립적으로 유지합니다.

### 6. 서로 다른 PC를 위한 그래픽 선택

```text
요구: 그래픽 성능이 다른 컴퓨터에서도 같은 경주를 즐길 수 있어야 한다.
결정: 상·중·하 품질과 첫 방문 그래픽 측정을 제공한다.
구현: 장면 에셋을 재사용하고 소품을 묶어 그리며 차량 LOD를 전환한다.
```

상·중은 NORMAL 차량 모델, 하는 LIGHT 모델을 사용합니다. 배경 설정도 작업량을 줄입니다. 지오메트리·재질 공유, 반복 소품 인스턴싱, 정적 장면 에셋 재사용으로 중복을 줄입니다. 품질 선택은 표현을 바꾸며 차량 물리는 바꾸지 않습니다.

첫 방문의 그래픽 측정은 품질을 선택하고 저장합니다. 측정 중에 사용자가 직접 선택한 경우를 포함해 수동 선택이 우선합니다. 기기별 초기 설정을 제안하는 기능이며 FPS를 보장하지 않습니다. 창의 가림 상태, 해상도, 브라우저 동작은 측정에 영향을 줄 수 있습니다.

### 7. 다음 경기를 쉽게 시작하기

```text
요구: 주행석이 가득 찼어도 짧은 쉬는 시간을 함께 쓸 수 있어야 한다.
결정: 차량 선택, 준비, 관전, 재경기를 이어지는 흐름으로 다룬다.
구현: 대기열을 유지하고 다음 경기의 상태를 화면에 보여준다.
```

로비, 대기 중, 결과 화면에서 차량을 선택할 수 있습니다. 관전자는 드라이버를 고르거나 자동 선두 관전을 사용합니다. 초대 링크로 반복 입력을 줄이고, 결과 카운트다운·대기열·재경기 준비 상태를 보여줘 지금 무엇을 기다리는지 알 수 있게 합니다.

### 8. AI와 협업하고 사람이 확인하기

```text
작업 흐름: 작은 요구를 논의하고 구현한 뒤 직접 플레이하며 문제를 확인한다.
사람의 역할: 우선순위, 주행감 검수, UI 방향과 변경 수용 여부를 결정한다.
AI 역할: Dots는 모델링, Codex는 네트워크·서버 구현,
         ChatGPT는 밸런싱 논의를 맡는다.
```

사람이 제품 결정, 플레이테스트, UI 방향, 우선순위, 수용 기준을 주도했습니다. Dots는 모델링을, Codex는 네트워크와 서버 구현을, ChatGPT는 밸런싱 논의를 도왔습니다. 이 구분은 이 프로젝트의 작업 방식이며 생성 결과의 정확성을 보장하지 않습니다. 변경이 잘 작동하는지는 테스트와 플레이테스트로 계속 판단했습니다.
